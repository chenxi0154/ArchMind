## 一、项目定位：秒出概况

用户选择文件夹后，先做一次快速扫描，秒出项目概况：

1. 扫描
   - 获取当前项目下的 `README` → README 概述
   - 继续获取配置文件
   - 获取入口文件
   - 获取依赖文件
2. LLM 分析 → 生成项目具体概况
3. 结果写入 SQLite，分成多个表：`projects`（项目记录）、`file_index`（文件索引）、`analysis_task`（分析任务队列）、`entities`

**概况描述字段：** 项目名称、项目描述、技术栈、主要功能、业务领域

**涉及技术：** Java NIO、File API；文档解析支持 markdown / pdf / word；overview 生成流程：文档 → 切片 → prompt → LLM → overview JSON

## 二、上传（项目上传与解析）

支持三种上传方式：

- Git 仓库拉取
- 本地选择文件夹
- ZIP 包上传

**ZIP 上传：**
- 前端需考虑：文件大小限制、文件类型、交互进度条、安全隐患
- 后端：解压项目，存放位置待定
  - GPT 做法：传到 AI 服务商的云服务器临时存储空间（DeepSeek 云端存储），分析完成后源文件和解压内容自动清除，不落数据库

**文件存放方式（TRAE 思路）：**
- TRAE 直接读取，有权限访问选定文件夹中的所有文件，直接读取和分析，不做任何搬移
- 优点：不用解压压缩包、不额外开辟空间、文件记录长期性可持续读取分析

## 三、TRAE 解析文件的流程（初始认知）

- 初始阶段：全局扫描，用 LS 和 Glob 工具列出文件夹层级结构，了解项目包含哪些子目录和文件类型
- 识别关键入口文件：优先查找并阅读高价值文件
  - README 项目说明 → 快速了解项目用途和架构
  - 配置文件 → 了解技术栈、依赖和构建方式
  - 入口文件 → 理解程序的启动流程
- 判断项目类型和规模：根据文件数量和类型，判断是小脚本 / 中型 / 大型，然后调整分析策略

## 四、项目画像

1. 全局扫描，建立对项目的初始认知：先读 README → 配置文件 → 依赖文件 → 入口文件
2. LLM 解析 README，获取项目基本内容得到 overview
3. 自动触发代码分析：AST 解析代码内容
   - 待决：如何解析？有规律地解析还是一次性全解析？
   - 待决：AST 分析结果存放到哪里？异步分析还是触发分析？
   - 待决：如何实现扫描上传的文件？
4. 完成上述文件解读后，按权重解析剩余代码（以业务为主）：
   1. 模型和配置：数据模型、实体类、数据表结构和关系、API 定义文件、接口文档
   2. 控制器和服务层
   3. 解释业务逻辑和领域行为 → 大致勾勒出可提取的 Capability
   4. 工具函数、常量定义、类型定义、测试文件等

**展示信息：** 项目类型、项目复杂度、代码规模、开发语言、团队规模、技术架构、数据库

## 六、业务领域地图

### 地图设计

- 多个模块构成整体地图，模块大小按代码体量调整，模块之间既独立又相联系
- 需包含：模块名称、模块体量

### 领域节点内容

- 领域节点：名称 + 简要描述
- 领域之间的关系：依赖、包含、数据流向
- 每个领域的体量：包含多少文件、节点大小等
- 分析状态：已分析 / 分析中 / 未分析

### 实现方式

输入假设：README（领域声明）+ Controller 列表 + Service + 包结构

**领域划分引擎：**
- 静态分析层
  - 扫描目录结构
  - 解析路由，确认业务端点
  - 解析模型，确认业务对象
  - 解析 import，构建依赖图
- LLM 语义层
  - 给每一个候选领域生成描述
  - 识别目录结构无法体现的隐含领域
  - 生成领域之间、领域本身的关系描述
- 交叉验证：代码实现

### 领域展开

**内容：**
- 该领域包含的子模块 / 文件列表
- 核心业务对象及其关系
- 主要 Capability 列表：独立 Capability 的描述
- 与其他领域的接口点（哪些函数被外部调用）

**实现：** 核心功能分析（理解代码由什么组成），用 AST 技术（JavaParser 或 Eclipse JDT，待定），LLM 理解分析结果 → 业务能力
