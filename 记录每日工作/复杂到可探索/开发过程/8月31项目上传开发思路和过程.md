## 架构误区和澄清点

### 我的设计：

上传---解压---扫描入库----内容读取

### 一、架构澄清点：文件内容不在上传流程里
	把文件内容放到扫描之后❌
[文件内容存放在哪]：内容不存数据库，留在磁盘上，file表只用于存放元数据（比如：path，size，hash，type）。

所以FileContentService不应该被upload调用，它的使用场景一个是后续AI分析阶段，拿到某个filePath后按需读取那一文件内容，真正的职责时序：
```
上传阶段：校验 → 落盘 → 建 source → 解压 → 扫描入库（只存元数据）
分析阶段（后续）：FileContentService.readTextContent(filePath)  → 读单个文件
```

### 二、Controller层的问题
参数设计的方向性错误。前端传上来的MultipartFile本质是内存字节或临时文件，不是一个稳定的磁盘路径。

- Controlller只做透传：把projectId+MultipartFile原样交给upload，不碰文件系统。
- 落盘路径（存到哪，叫什么）是uploadService的内部存储决策。

**return 只返回 projectId 不够。** 上传完成后调用方真正需要的是后续查询的凭据——`sourceId`（`project_source` 主键，后面查分析状态、关联文件都要用它），以及状态、文件名、大小。所以需要一个 `UploadResponse`（你实体里已经有这个 DTO 的雏形，含 `sourceId/projectId/fileName/fileSize/status/taskId`）。

### 三、upload的参数问题

两个参数都有问题：
1. **`目的路径` 不该由外部传入。** 存储布局（比如 `{baseDir}/{projectId}/{sourceId}/`）是 `UploadService` 的内部职责。由 Controller 决定落盘位置，会造成 Controller 与存储结构耦合，而且外部传入的路径本身就多了一个路径穿越攻击面。应该收 `projectId + MultipartFile`，路径在内部生成。
2. **`return 解压路径` 是把内部实现细节泄露给上层。** Controller 拿到解压路径干什么用？它不该去碰那个目录。应 return 一个结果对象（`UploadResponse`），解压路径只留在 Service 内部（顶多写进 `project_source.content` 留档）。

另外 `upload` 里少了一步你流程里写了但伪代码没体现的：**创建 `project_source` 记录**。而且建议先建 source 拿到 `sourceId`，再用它作为目录名的一部分——否则后面回填 `content`/`fileId` 时没有锚点。

### 四、遗漏场景

安全红线：
按严重程度列，前三条是安全红线：

| 场景                   | 说明                                                                    |
| -------------------- | --------------------------------------------------------------------- |
| **Zip Slip 路径穿越**    | 压缩包内条目名是 `../../etc/passwd`，解压会写到目标目录之外。必须 normalize 后校验仍在目标目录内       |
| **解压炸弹**             | 一个小 zip 解压出 GB/TB 级内容。要限制条目数量、单文件大小、解压总大小                             |
| **假 zip**            | 只把后缀改成 `.zip` 的非压缩文件。校验 `PK` 魔数                                       |
| 中文文件名乱码              | zip 文件名没有统一编码，GBK 打包、UTF-8 读会乱码，Java 默认按 UTF-8                        |
| 符号链接条目               | zip 里可以塞 symlink，解压后指向系统任意路径                                          |
| 解压失败半成品              | 解压到一半抛异常，留下的半解压目录要清理，`project_source` 状态要标记失败                         |
| 事务一致性                | Scanner 往 `file` 表插到一半失败，`project_source` 和 `file` 表不一致，需要失败标记 + 回滚策略 |
| `projectId` 不存在 / 归属 | 项目不存在、或不属于当前登录用户，要拦                                                   |
| 重复上传                 | 同一 project 重复上传，是覆盖旧数据还是追加？要定策略                                       |
| 空 zip / 只有目录         | 解压出来没有文件，扫描结果为空                                                       |

### 五、Extract 和 Scanner 的参数与 return

```
Extract(压缩包文件路径，解压后的目的路径) {  1. 参数是否存在  2. 如何解决  return 目的路径？}
```

参数基本 OK，但要补两个校验：压缩包存在且是普通文件、目的路径能创建。**return 目的路径是对的**，但要明确 return 的是「解压后的根目录」。一个要提前约定的点：如果 zip 里有一层顶层目录（很多 zip 都这样），解压根到底是 `target` 还是 `target/项目名`？建议约定「解压到的就是扫描根目录」，Scanner 按实际结构走，不要假设层级。

```
Scanner(目的路径) {  1. 参数校验是否为空  2. 如何扫描并记录到file  3. return什么？}
```

参数不够：**还缺 `projectId`**（`file` 表每条都要 `projectId`），以及可选的根节点 `parentId`。

**return 什么**：建议 return 扫描出的 `List<FileEntity>`（首元素是根目录），或者至少 return 根目录的 `fileId`。原因：`upload` 需要拿根目录的 id 回填 `project_source.fileId`，后续分析也需要这个入口。

### 六、如何解压，如何扫描

**解压**：

1. 用 `ZipInputStream` 逐 entry 流式读，不要整包 `readAllBytes` 进内存。
2. 每个 entry：`targetDir.resolve(entryName).normalize()` 后 `startsWith(targetDir)` 校验（防 Zip Slip），不通过直接抛异常。
3. 目录 entry 建目录，文件 entry 先建父目录再 `Files.copy`。
4. 循环里累计条目数和字节数，超限即止。

**扫描**：

1. 递归遍历（或 `walkFileTree`），目录和文件**都要**入库，靠 `parentId` 建立父子关系。**根目录本身也要有一条记录**，否则目录层级表达不全、`project_source.fileId` 也没法指向根。
2. 先插父节点拿到自增 id，再遍历子节点把该 id 设为 `parentId`。
3. 目录记 `fileType='dir'`、`size=0`；文件记 `'file'` 和实际大小。`filePath` 存相对根目录的 POSIX 风格路径（`/` 分隔，跨平台稳定）。
4. 扩展名 → `language`，文件算 SHA-256（超大文件跳过避免耗时）。

## Controller
接收参数，调用方法，return 结果；
**注解目的**：
@RestController：
给类的身份标签，告诉Spring容器，这个类是用来处理HTTP请求的后端接口
- 它是`@Controller` + `@ResponseBody`的组合注解，专门用来写 RESTful 风格的接口。
- 必须是加在controller类上，Spring才会把这类接口当成接口处理器来管理

@RequestMapping：
给类和方法贴的路由总开关，用于绑定请求的URL路径，请求方式，请求头等，是最通用的路由注解，统一接口前缀。
- 可以加在类上，也可以加在方法上
- 致辞配置method属性指定请求方式，也支持不指定，匹配所有请求方式
- 是请求映射注解的父注解

@RequiredArgsConstructor
生成构造器，用于依赖注入
- Spring 的 Controller、Service、Component、Filter、Handler；
- 类依赖其他 Bean；
- 希望使用构造器注入；
- 依赖创建后不应变更，因此字段通常写 final。

```java
@RestController
@RequestMapping("/projects")
@RequiredArgsConstructor
public class ProjectSourceController {

    private final ProjectUploadService projectUploadService;

    @PostMapping("/{projectId}/upload")
    public Result<?> upload(
            @PathVariable Long projectId,
            @RequestParam("file") MultipartFile file) {

        projectUploadService.upload(projectId, file);

        return Result.success();
    }
}

```
