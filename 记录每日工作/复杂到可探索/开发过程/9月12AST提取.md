## 三、阶段 A 设计：三趟原则

AST 解析必须**分三趟**，因为信息依赖决定了顺序不能乱：

| 阶段 | 做什么 | 输入 | 输出 | 能否边做边连边 |
| --- | --- | --- | --- | --- |
| **A 解析** | JavaParser 抽声明 + 悬空调用 | 每个文件的源码文本 | 类/方法/字段 + 调用记录（只知道名字，不知道指向谁） | ❌ |
| **B 建索引** | 把声明整理成查找字典 | A 的全部声明 | 三张 HashMap（类索引/别名索引/方法索引） | ❌ |
| **C 关系解析** | 拿字典给悬空调用定名 | A 的调用记录 + B 的字典 | 真正的边（CALLS/EXTENDS/…） | ✅ 这步才第一次"连上线" |

**为什么不能边解析边连边**：`userService.save()` 里的 `UserService` 可能定义在另一个文件——解析当前文件时字典里根本没有它，没法定名。必须**先把全项目声明攒齐（A+B），再统一消解（C）**。

| 文件 | 字段 | 用途 |

| 文件 | 关键字段 | 用途 |
| --- | --- | --- |

| `ParsedProject` | files | 总容器 |

`ClassKind`：CLASS / INTERFACE / ENUM

## 五、AstParserServiceImpl 核心逻辑

### 主循环

```
for file in files:
    cu = parser.parse(file.content)     // JavaParser BLEEDING_EDGE
    extractFile → ParsedFile → 加入 ParsedProject
    // 解析失败：catch → log.warn + continue（不拖垮整批）
```

### 抽文件（extractFile）

- packageName（默认包为空串）
- imports（`cu.getImports()`）
- 遍历 `cu.getTypes()` → extractType（含嵌套类打平）

### 抽类（extractClass）

- qualifiedName = packageName + "." + simpleName（嵌套类追加外层名）
- kind：`isInterface()` → INTERFACE，否则 CLASS
- extendsTypes / implementsTypes：**存原始短名**（`"BaseController"`），消解留给 C
- 字段：一行可声明多变量（`int a, b;`），遍历 `getVariables()`
- 方法+构造器：**两个来源**，`getMethods()` + `getConstructors()`，别漏

### 抽方法（extractMethod）—— 最重

1. **签名**：`name + "(" + 参数类型逗号连接 + ")"`
2. **作用域类型表**（localTypes）：
   - ① 参数 → `put`
   - ② 局部变量 → `putIfAbsent`（不遮蔽参数）
   - ③ 本类字段 → `putIfAbsent`（不遮蔽参数/局部变量）
   - this/super 由 C 阶段处理
3. **悬空调用**（calls）：
   - `findAll(MethodCallExpr.class)` → `ParsedCall(receiver, methodName, argCount, line)`
   - `findAll(ObjectCreationExpr.class)` → `new Foo()` 记成 `ParsedCall("Foo", "<init>", ...)`
   - 同方法内去重（`receiver|method|argCount` 做 key）

### 两个 JavaParser 坑（踩过）

1. **构造器不在 `getMethods()` 里**，必须单独 `getConstructors()`
2. **`getMembersOfType()` 在 3.25.10 不存在**（API 变了），改用 `getMembers().stream().filter()` 手动过滤嵌套类
3. **`NodeWithAccessModifiers` 包路径变了**：3.25.10 在 `nodeTypes.modifiers.NodeWithAccessModifiers`（不是 `nodeTypes.NodeWithAccessModifiers`）
